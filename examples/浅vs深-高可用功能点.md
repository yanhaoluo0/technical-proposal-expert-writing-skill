# 示例：功能点描述「浅 → 深」（高可用）

> 用途：演示深度写作协议的效果。正文按标书叙述体、零分点书写；本示例用于借鉴结构与深度，不是唯一答案。

## 浅（泛泛而谈）

本系统采用高可用架构，通过集群部署与故障转移机制，保证系统 7×24 小时稳定运行，满足 99.9% 可用性要求。

**问题**：只有「高可用」「集群」「故障转移」概念词，没有架构权衡、具体机制、验证手段；去掉修饰词后没有实质内容，评审无法追问、无法核验。

## 深（借技术卡片 + 六问展开）

针对本标书对系统可用性的要求，本方案在高可用设计上采用「负载均衡 + 主备集群 + 自动故障转移」的组合架构。之所以不直接选择双活方案，是考虑到本系统业务写入模型为单点强一致，双活需要引入分布式锁与冲突仲裁，复杂度上升带来的收益有限；主备方案配合自动化切换，在满足可用性目标的同时保持架构的可维护性。数据库主备间采用半同步复制，正常工况下 RPO 控制在秒级，既避免同步复制带来的写入放大，也避免异步复制在故障时丢失较多数据。应用侧由网关统一收口流量，节点通过探活接口上报健康状态，故障时由仲裁节点判定并触发虚拟 IP 漂移，业务在分钟级完成恢复。该方案每年组织不少于一次的故障注入演练，将切换流程固化为预案并记录实际切换时长，使 99.9% 可用性指标具备设计依据与验证手段，而非空泛承诺。

## 对照要点

- 六问覆盖：问题对应（可用性指标）、选型权衡（主备 vs 双活）、机制（半同步复制 / VIP 漂移 / 仲裁）、工程化（探活接口 / 演练预案）、验证（故障注入）、风险（双活复杂度）
- 有具体技术名词与数据流，评审可追问、可核验
- 指标（99.9%、RPO、RTO）均有实现手段支撑，数值未编造
