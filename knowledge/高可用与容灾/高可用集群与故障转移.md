# 高可用集群与故障转移

## 适用场景与触发词

政务/企业关键系统、7×24 小时在线业务；标书或设计报告出现「高可用」「故障转移」「集群」「双活」「RPO/RTO」「可用性 ≥ 99.x%」时命中。

## 技术内涵与边界

- 做什么：消除单点故障（SPOF），某节点失效后自动或半自动恢复，对外持续可用
- 不做什么：不等于「负载均衡」。负载均衡是流量分发，高可用是故障恢复；两者常组合使用，但文档要写清各自职责

## 典型架构与关键机制

- 主备（Active-Standby）：备机同步主库数据，主故障后切换；结构简单，切换存在秒级到分钟级中断
- 双活/多活（Active-Active）：多节点同时服务，故障后流量切换，中断更短；要求数据一致方案与冲突处理，复杂度更高
- 关键组件：负载均衡/网关（流量入口）、心跳与健康检查（故障探测）、虚拟 IP（VIP 漂移）、仲裁节点（防脑裂）、配置中心
- 数据机制：数据库主从复制（同步/半同步/异步）、消息与日志同步、存储双写或共享存储

## 关键设计决策与权衡

- 可用性指标决定架构复杂度：99.9% 与 99.99% 对应的切换要求与成本显著不同
- 同步复制 RPO 趋近 0 但增加写入延迟；异步复制性能好但故障时可能丢失最近写入——按业务选型并在文档中写清取舍
- 主备 vs 双活：双活不必然更高可用，复杂度过高反而引入更多故障面；多数场景「主备 + 快速切换」已满足

## 工程化要点

- 健康检查区分「进程活但业务僵死」：探活接口优先于 ping
- 切换自动化并定期演练：故障注入演练要记录实际切换时长
- 部署考虑仲裁与隔离，避免脑裂后双主写库；监控覆盖节点状态、复制延迟、切换事件

## 指标映射

| 指标 | 口径示例 | 支撑手段 |
|---|---|---|
| 可用性 | 年可用性 ≥ 99.9%（年停机 ≤ 8.76 小时） | 主备 + 自动切换 + 演练 |
| RPO | 灾难恢复时最多丢失 X 分钟数据 | 同步/半同步复制 |
| RTO | 故障后 X 分钟内恢复服务 | 自动探测 + VIP 漂移 + 预案 |
| 并发 | 峰值 TPS / 并发连接数 | 负载均衡 + 水平扩展（配合高可用） |

## 标书化叙述示例（片段）

本系统采用「负载均衡 + 主备集群 + 自动故障转移」的高可用架构。数据库主备间采用半同步复制，正常工况下 RPO 控制在秒级；应用节点通过探活接口上报健康状态，故障时由仲裁节点判定并触发虚拟 IP 漂移，业务在分钟级完成恢复。每年组织不少于一次的故障注入演练，将切换流程固化为预案并记录实际切换时长，使可用性指标具备设计依据与验证手段，而非空泛承诺。

## 风险与边界

- 禁止编造具体可用性数值；指标值必须由用户提供或标记「待确认」
- 双活方案需明确冲突解决与数据一致性边界，否则评审会被追问
- 区分「服务级高可用」与「数据级高可用」，文档需分别说明
