## 一、Pattern: Microservice Architecture 骨架

### Context（背景）

- 业务关键型企业应用
- 需快速、频繁、可靠交付变更——以 DORA 指标衡量
- 工程组织按 Team Topologies 拆分为小型、松耦合、跨职能团队
- 团队按 DevOps Handbook 实践持续部署
- 团队以自动部署流水线交付小而频繁的变更

### Problem（问题）

如何把多个 subdomain 组织成一组可部署/可执行的组件？

### Forces（驱动力）

Chris Richardson 提出「dark energy + dark matter」二元框架。

**Dark Energy Forces（推动拆分的力）**：

- Simple components——简单组件（少 subdomain）更易理解维护
- Team autonomy——团队独立开发、测试、部署
- Fast deployment pipeline——快速部署流水线
- Support multiple technology stacks——支持多技术栈
- Segregate by characteristics——按特性（资源/可用性/安全）隔离

**Dark Matter Forces（阻碍拆分的力）**：

- Simple interactions——本地或少量交互优于分布式
- Efficient interactions——大量网络往返、大数据量传递低效
- Prefer ACID over BASE——ACID 事务比最终一致 saga 更易
- Minimize runtime coupling——降低运行时耦合提可用、降低延迟
- Minimize design time coupling——降低设计时耦合，避免锁步变更

### Solution（解决方案）

- 应用拆分为**两个或多个独立可部署、松耦合的组件（服务）**
- 每个服务包含一个或多个 subdomain
- 每个 subdomain 仅属于一个服务（共享库 subdomain 例外，可被多个服务共用）
- 服务由拥有其 subdomain 的团队所有
- **API 网关** 通常作为应用入口
- 分布式系统操作由**服务协作模式**（Saga / Command-side replica / API composition / CQRS）实现
- 每个服务独立源代码仓库与独立部署流水线

### Resulting Context（结果）

**收益**：

- 服务简单（少 subdomain），易理解维护
- 团队自治（独立开发测试部署）
- 部署流水线快（服务小、独立部署）
- 支持多技术栈
- 按特性隔离 subdomain（扩展性/可用性/安全）

**潜在缺点**：

- 部分分布式操作复杂、难调试
- 部分分布式操作低效
- 部分操作需用最终一致（saga）替代 ACID 事务
- 部分分布式操作涉及运行时紧耦合，降低可用性
- 可能出现设计时紧耦合，导致锁步变更

## 二、相关模式清单（按类别）

> 写作时可在「本项目采用的微服务模式」清单中按本节分类引用。每个模式的中文翻译为非标准译名，建议**保留英文术语**或与官网一致。

### 2.1 服务协作模式（Service Collaboration Patterns）

跨服务实现的分布式操作模式：

- **Saga**——把分布式命令拆为一系列本地事务
- **Command-side replica**——把只读数据复制到执行命令的服务
- **API composition**——把分布式查询拆为一系列本地查询
- **CQRS**——把分布式查询拆为一系列本地查询（与 API composition 并列；按读模型分离场景使用）

### 2.2 数据模式（Data Patterns）

- **Database per Service**——每服务独立数据库，确保松耦合
- **Transactional Outbox**——原子更新业务实体并发消息（与 Saga / CQRS 配套）

### 2.3 通信风格（Communication Style）

- **Messaging**（消息）
- **Remote Procedure Invocation**（远程过程调用）

### 2.4 服务发现（Service Discovery）

- **Client-side Discovery**（客户端发现）
- **Server-side Discovery**（服务端发现）

### 2.5 可靠性（Reliability）

- **Circuit Breaker**（熔断器）

### 2.6 安全（Security）

- **Access Token**（访问令牌）

### 2.7 可观测性（Observability）

- **Log aggregation**（日志聚合）
- **Application metrics**（应用指标）
- **Audit logging**（审计日志）
- **Distributed tracing**（分布式链路追踪）
- **Exception tracking**（异常追踪）
- **Health check API**（健康检查 API）
- **Log deployments and changes**（部署与变更日志）

### 2.8 测试模式（Testing Patterns）

- **Service Component Test**（服务组件测试）
- **Service Integration Contract Test**（服务集成契约测试）

### 2.9 UI 模式（UI Patterns）

- **Server-side page fragment composition**（服务端页面片段组合）
- **Client-side UI composition**（客户端 UI 组合）

### 2.10 部署模式（Deployment Patterns）

- **Single Service per Host**（每主机单服务）
- **Multiple Services per Host**（每主机多服务）

### 2.11 跨切关注（Cross-Cutting Concerns）

- **Microservice chassis pattern**（服务底盘模式）
- **Externalized configuration**（外部化配置）

### 2.12 入口（Entry Point）

- **API Gateway pattern**（API 网关模式）

### 2.13 替代架构（Alternatives）

- **Monolithic architecture**（单体架构）——微服务架构的替代方案

## 三、已知使用者（Known Uses）

- **Netflix**——视频流媒体服务，承担约 30% 互联网流量，每天处理超 10 亿次视频流 API 调用，800+ 设备类型；每次 API 调用平均扇出到 6 个后端服务
- **Amazon.com**——最初两层架构，为扩展演化为数百个后端服务；网页应用调用 100-150 个服务来组装页面
- **eBay**——从单体演化为面向服务架构，应用层多个独立应用，按 X、Y、Z 轴拆分扩展
