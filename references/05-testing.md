# 05 测试阶段

先读 [../writing-guidelines.md](../writing-guidelines.md)。功能编号与 SRS / 提测单保持一致。

## 测试用例表

**模板**：`文档示例/05 测试阶段/01 测试用例/测试用例表 - 模板.xlsx`

表头：项目名称、测试负责人、小组人员、更新日期。

每条用例列名固定：

| 序号 | 测试用例编号 | 测试用例标题 | 预置条件 | 步骤名称 | 步骤描述 | 预期输出 | 实际输出 | 优先级 | 编写人 | 执行结果 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 |  |  |  |  |  |  |  |  |  |  |

### 规则

- 用例编号单独成体系时可写 `TC-{模块}-{三位}`，并在表前用一句话声明；若用户要求与需求编号绑定，在标题或预置条件中引用需求编号
- 步骤名称 + 步骤描述必须可执行（「点击【保存】」而不是「验证保存功能」）
- 预期输出可观察（页面提示原文、库表变化、状态码）
- 未执行时：实际输出、执行结果留空或填「未执行」，不要填「通过」
- 优先级用高/中/低或 P1/P2/P3，全文统一

## 测试计划

**模板**：`文档示例/05 测试阶段/03 测试计划/测试计划 - 模板.docx`

### 大纲

1. 概述
   - 1.1 项目简介
   - 1.2 业务流程
   - 1.3 范围及目的
   - 1.4 限制条件
   - 1.5 参考文献（至少列需求规格说明书、数据库设计说明书、接口设计说明书；没有的标「待确认」）
2. 一般要求
   - 2.1 测试目标
   - 2.2 接收标准（必须可判定通过/不通过）
   - 2.3 资源和工具（人力资源 / 测试环境 / 工具）
3. 测试类型及性能测试方案
   - 3.1 兼容性测试
   - 3.2 性能测试（脚本开发 / 场景设置 / 指标监控及分析方案）
4. 测试任务及进度
5. 系统风险及优先级
6. 提交测试物

### 固定风险句（可改数字，不可删掉这类约束）

模板强调：冒烟测试不通过必须打回重新提测，并评估对进度的影响。风险章要写：

> 若开发提交的测试版本冒烟测试未通过，该版本必须打回重新提交；由此造成的进度延误需在第 4 章进度中体现或标注偏差。

接收标准示例句式：

> 冒烟用例 100% 通过；本轮阻塞/严重缺陷为 0；剩余开放缺陷均有书面豁免。

## 系统测试报告

**模板**：`文档示例/05 测试阶段/02 测试报告/系统测试报告 - 模板.docx`

### 大纲

1. 概述
   - 1.1 项目简介
   - 1.2 测试概要（项目情况 / 测试人员 / 周期 / 测试轮次）
   - 1.3 测试对象（表：一级菜单、二级菜单、开发负责人、测试负责人、是否通过、BUG 数）
   - 1.4 测试总体执行情况（提测时间、部署完成时间、测试结束时间、执行用例数、通过用例数、发现 BUG 数、严重级别分布）
2. 测试分析
   - 2.1 BUG 趋势分析
   - 2.2 本版本各模块 BUG 严重级别分布
   - 2.3 本次测试中发现 HIGH 级别以上的 BUG（表：序号、一级菜单、二级菜单、BUG 说明）
   - 2.4 测试进度分析（计划/实际开始结束、偏差天数、原因、解决方案）
   - 2.5 测试过程中遇到的问题及解决方案
3. 度量数据收集
4. 附件

无真实测试数据时：数字列填「待确认」，结论写「数据待填，结论暂缺」。**禁止编造通过率和 BUG 数。**

## 检查清单

- [ ] 用例步骤可执行、预期可观察；未执行不标通过
- [ ] 计划含接收标准、冒烟打回规则、参考文献
- [ ] 报告对象表与执行情况表列名未改
- [ ] 无编造度量
